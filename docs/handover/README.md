## 这个项目是什么

一套 shell 脚本, 把 mihomo Meta 内核包装成一个可交互配置的节点部署面板。

- **服务端**: 生成 mihomo 配置片段 → 校验 → 重载 → 部署内核
- **客户端**: 管理面板、本地节点、订阅、测速、DNS、Web UI
- **全协议一键生成**: 一次生成一组覆盖不同协议/传输/加密方式的节点
- **CDN**: 可选走 Cloudflare, nginx 负责回源
- **一次性分享链接**: 生成 N 次 / M 小时后失效的订阅链接

**规模**: 328 次提交,约 21000 行 (shell + python),13 项机械校验门。

## 三条最重要的经验

写在最前面, 因为这个项目绝大多数 bug 都是这三种形态。

### 1. 「静默失败」是这个项目的主要敌人

这个项目出现过的 bug 里, **绝大多数不报错**。表现是"面板节点都在, 就是连不上", 或者"界面正常, 但某个设置没生效"。

最典型的一次: 客户端 DNS 配错导致 ECH 整体失效、全部 CDN 节点连不上,而日志里**没有任何一条指向 DNS**。排查花了整整三轮。

对应的习惯: **发现异常时, 不要相信"看起来正常"的部分**。要主动去问"这一步到底有没有执行",而不是假设它执行了。

### 2. 不要因为"看起来失败了"就关掉一个功能

ECH 曾经因为"实测 7 个 CDN 节点全连不上"而被判定为有问题,并改成默认关闭。后来查清楚根因在客户端 DNS,**与 ECH 无关**,于是改回开启。

关掉一个功能很容易 —— 但那只是把证据擦掉了。**先找原因, 再决定要不要关**。

### 3. 探针要「问」,不能「假设」

这个项目栽过的跟头, 大部分是**测量方法本身是错的**:

| 探针 | 错在哪 |
|---|---|
| 看 nginx 日志返回 200 就认为 CDN 正常 | 200 只说明请求到了源站, 后面几层还没验 |
| 查路由器 DNS 能不能解析 type 65 | 解析器不是关键, **谁被选中**才是 |
| `systemctl restart` 之后立刻查端口 | 重启是异步的, 监听还没绑上 |
| 在 for 循环里用 `${*// /-}` 换字符 | zsh 下不替换, bash 下才替换 |
| 用 `grep` 匹配文件名前缀 | 前缀不是文件名, 是文件里的一行 |

**教训**: 每次得出"某功能坏了"的结论前,先问一句"我测的是不是我以为的那个东西"。
